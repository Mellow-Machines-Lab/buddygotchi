Boop's architecture

How Boop's pieces fit together, and what each one sends to the next. The code is the detail: each piece below names where it lives, and the packages' own ARCHITECTURE.md files explain them.

Updated 2026-10-22.

The shape Where the pieces join

The shape

Boop is a Mac app plus a small screen on your desk. Data flows one way: from your coding agents (Claude Code, Codex), through the Mac app, to the device. Boop only watches and reports. It never approves or blocks anything an agent does. Three packages handle the general parts (reading agent hooks, asking the multiple-choice model, talking to the device), and they know nothing about Boop or each other. Boop's own code connects them.

Below, one Claude Code turn finishes and we follow it through. Each row shows a piece on the left and what it sends next on the right. The examples come from a real run, cut short where you see ….

  2. the new event
  3. Core: the rules

    Applies Boop's fixed rules: the session is now idle, so the screen changes. The new screen state goes to the device right away, before Jev is asked anything.

    state to the device, through LinkKit 
    {
  "t": "state",
  "base": "idle",
  "mood": "calm",
  "busy": 0,
  "idle": 1,
  "vol": 6,
  "when": ["day"]
}
    idle and helpers count sessions waiting for your next prompt and helpers at work; when is what's true now (Occasions: the part of the day, a holiday, a milestone day), and the board picks each look's variation itself from the designs whose tags are all on. The prompt's heading says the calendar's in words (14:05, Saturday, Halloween).
  4. the event, read from the transcript
  5. View: sentences for Jev

    TranscriptView writes the event as a sentence Jev can read, using earlier events for context, such as when the turn started and how many tools it used. It counts runs on the line, as it does pokes: a check failing again, quick wins in a row (in streaks of five), the check-ins on a long turn (in rounds of four), a barrage again. It also says what the brain would otherwise miss: you answering a request, a compacted context, a poke while Boop sleeps, and idle check-ins while you're around and no agent works. Jev answers the same line the same way, so each rung of a run gets a line of its own. A finished turn is worth asking Jev about.

    The end of the prompt Jev reads 
    HISTORY (oldest first; indented lines add to the line above)
1 min ago: claude started turn 1 on "api".
  You asked: "Fix the flaky login test"

NOW (14:26, Monday)
claude finished turn 1 on "api": done, a long turn, 3 tool calls.
  Its last message: "Fixed the flaky login test; all 42 tests pass."
Boop did nothing on its own.
  6. the sentence, with recent history
  7. MellowHarness + Jev package

    Builds the prompt: Boop's personality, the nature you chose at setup (sweet or cheeky) and its rules (the steering files), then recent history, then the new event. It asks all of Boop's questions in one request to Jev, the multiple-choice model. Every question is multiple choice, and each option says when it applies and when it doesn't.

    Two of the questions (options trimmed), and the answers

  …
react.mood: none | calm | comfy | lazy | bored | pleased | …

mood calm · react.mood excited · react.animation success
react.loops once · say.feeling none · say.about start · say.kind word
    From a test run with a stand-in for Jev that always gives the same answers, which is why a finished turn gets the topic "start". Jev answers the same questions, with a probability for each option.

LinkKit (linkkit/)
  1. LinkKit

    Carries the messages over Bluetooth or USB. On the board it keeps the queue: one do plays at a time, and a next waits for the one playing to finish, up to its ttl (5 s here), then plays.

    ended back to the Mac, once per do 
    {
  "t": "ev",
  "kind": "ended",
  "data": { "id": 558386703, "how": "done" }
}
    Boop marks the reaction finished, and the next prompt tells Jev what Boop did.
state and do down · ended and taps back up
  1. The device (firmware/)

    Draws the face and plays the clip. There are two boards: the CYD, with a pixel-art face, and the AMOLED, with a soft gel face. A tap reacts on the board at once, then is reported to the Mac.

    A tap, going back to the Mac 
    {
  "t": "ev",
  "kind": "tap",
  "did": "poked",
  "data": { "src": "screen" }
}
    Boop records it as a poke, which also prompts Jev. BOOT's says "src": "button", and "did": "handoff" when it handed you an agent.

Three speeds

SpeedRuns onHandlesNever waits for
Reflex (instant)The deviceReacting to taps, blinking, showing that an agent needs you, the queue (the order reactions play in)The Mac
Reactive (fast)The Mac's rulesA hook changing the screen, or a rule's reactionJev
Deliberative (slow)MellowHarness and JevEvery mood change and reaction, including to a finished turnNothing, and nothing waits for it

Each speed's time budget is in internal/VERIFICATION.md §8.

Where the pieces join

Each package has its own vocabulary: agent-hooks has AgentEvents, MellowHarness has Events and lines, LinkKit has state, do and ev. Boop translates between them in the places below. Everything sent to the device goes out through Runtime, which is split by job over seven files in app/BoopKit/App/: Runtime.swift, and Runtime+Brain, +Buddies, +Device, +Talk, +Status and +Dev.

From → toWhereWhat happens
agent-hooks → BoopAdapter.event(from:), Runtime.hookEach hook line becomes an AgentEvent, kept as a MellowHarness Event with its facts in data
agent-hooks → the rulesCoreagent-hooks' SessionTracker tracks each session and whether an agent needs you. The core adds what the screen shows, what takes priority, and the rules' reactions
Boop → MellowHarnessPipelineEach event is written to the transcript and run through the core's rules in one step. TranscriptView defines the sentence for each kind of event, reading each session and its turn from a SessionTracker of its own, fed the same events as the core's, so the two agree. Runtime registers the two outputs, mood and react
Boop → LinkKit (what the screen shows)Runtimelink.update(state:) on every change, on connect, in answer to hello and every 10 s
Boop → LinkKit (a rule's reaction)Runtime.playRuleplay: if_free: sent at once, and skipped unless nothing plays on the device or what plays is resting. The core records each one it plays, so the next prompt says Boop already reacted on its own (a turn's starting is recorded but left out of the prompt). Push-to-talk's listening after the app's mic button is play: now
Jev → LinkKit (reactions)ReactOutput → Runtime.queueplay: next with a 5 s ttl. The reaction stays in progress until the device's ended, which Reactions reads
Boop → which deviceDeviceChooserThe board over Bluetooth, or, while one runs on this Mac and Settings is told to use it, the simulator (simulator/: the firmware's own code in a web page) over its USB socket. Nothing above the transport knows which
A demo → BoopRuntime.playA character pack's script (demo/demo.jsonl, or another in demo/) comes in through the same doors as real work: the agent's hooks as hooks (sent by the player, or with --live a real agent's, which the rest keeps to), a poke as the device's, talk as the mic's; the brain's steps are forced passes. DemoRecorder keeps what the device was sent, for the simulator's page to play back
LinkKit → BoopRuntime.device, Runtime.deviceEventA tap becomes a poke through the pipeline, or, BOOT's when the board handed you an agent (did: handoff), a press, which opens the next one in line (Core.pressed: who needs you, then who finished last); talk_on and talk_off go to the core, which keeps push-to-talk, as it does for the app's mic button: it says when the Mac's mic goes on and off and when listening ends, records each step as a listen event with no sentence, and the runtime carries it out
Several buddies → one transcriptBuddy, Pipeline, Runtime+BuddiesBoop runs one buddy or several side by side, each a board with its own character pack, core and agents, all equals; one is the same code with a list of one. The pipeline owns every buddy's core, and BuddyBinding gives each agent session to one buddy (the one whose agents name it, else the least busy). With several, each event about a buddy is tagged with it (data.voice, Event.buddy), and each buddy is one of MellowHarness's voices: the brain answers an event once for each buddy, its own first, in a prompt that opens with whom it answers for (Buddy.header) and asks only that buddy's outputs, each built with its pack. A buddy's reaction becomes an event of its own (reacted, from the pipeline) that wakes the others, one more in its chain when it answers another's; past Buddy.maxRepliesInARow it no longer wakes anyone
